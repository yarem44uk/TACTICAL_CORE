## Purpose

WO-037-05 defines the operator-layer authentication and access-control boundary for the
separate FastAPI Operator Service (ADR-011 §15). It is a specification Work Order. It does
NOT authorize implementation of authentication; implementation requires a separate
explicit authorization following an independent forensic audit of this specification.

WO-037-05 is the successor to WO-037-04 (SSE realtime). It closes the documented
operator security gap while preserving every WO-037-01..04 invariant and the ADR-011
durable-core isolation boundary.

## Architectural Objective

Provide a minimal, offline-compatible authentication and access-control gate at the
operator layer so that operator REST and SSE endpoints and the operator UI are not
reachable without a locally configured credential.

```
Browser
   ↓
Operator Auth Guard  (NEW — WO-037-05)
   ↓
Operator Router      (existing)
   ↓
Operator Service     (existing)
   ↓
Authoritative Read-Only Repositories (existing, untouched)
```

SSE:

```
Browser
   ↓
Authenticated SSE GET /api/v1/operator/events/stream
   ↓
Operator Router
   ↓
Authoritative Event Repository (existing, untouched)
```

Key architectural invariant: authentication MUST remain entirely inside the operator
layer. NO durable-ingestion component (EventPipeline, DurableDeliveryDispatcher,
ReconstructionService, projection, checkpoint, source adapters) may depend on or be
modified by authentication.

`docs/SPRINT_REFACTOR_REPORT.md` ("Add authentication layer (High) - Before production
deployment"). ADR-011 §15 states "Optional local bearer/header authorization may be
implemented. Full RBAC is outside the MVP. Authentication must never become a dependency
of durable ingestion."

## Scope (IN SCOPE)

- Operator-layer authentication (verify a locally configured credential).
- Operator-layer authorization (gate access to operator REST, SSE, and UI).
- Protection of REST endpoints under `/api/v1/operator/*`.
- Protection of the SSE endpoint `GET /api/v1/operator/events/stream`.
- Protection of the operator UI (index + static assets).
- Safe local configuration of the operator credential/token (environment-based, not

- Security failure responses (401/403/500 contract).
- Security-related automated tests.
- Security headers (CSP, X-Content-Type-Options, Referrer-Policy, X-Frame-Options/
  frame-ancestors, Cache-Control) as MUST/SHOULD where justified below.

## Out of Scope (explicitly excluded)

- Full RBAC (role-based access control).
- User management system.
- Identity provider / SSO / external identity.
- Durable-core authentication.
- EventPipeline authentication dependency.
- Source adapter authentication.
- Database encryption at rest.
- TLS / HTTPS infrastructure (transport encryption) at the operator process.

- Reverse proxy architecture.
- Central IAM.
- Cloud identity.
- Rate limiting / connection limits (see Deferred Items).

Nothing outside the operator layer may be added. WO-037-05 does not introduce a second
database, second event store, or any durable authentication state.

## Architecture

The recommended architecture is a FastAPI dependency-based auth guard applied to the
operator router. All operator routes (REST + SSE + UI index/static) pass through the
guard. The guard is operator-local; it has no coupling to the durable core.

```
Browser
   ↓
Operator Auth Guard (dependency on every operator route)
   ↓
Operator Router
   ↓
Operator Service
   ↓
Authoritative Read-Only Repositories
```

The auth guard validates the presented credential against a locally configured expected
credential. It never writes anything, never creates state, and never touches the durable
repositories.

## Authentication Model

Recommended model: **Option A — Local Bearer Token** using the standard
`Authorization: Bearer <token>` header.

Rationale:
- Minimal; no new third-party dependency (stdlib constant-time comparison via
  `secrets.compare_digest`).
- Compatible with offline / air-gapped operation (fully local, no network, no external
  identity service).
- Operator-local; never a durable-ingestion dependency.
- Uses the standard Authorization header (interoperable, not a bespoke header).

Option B (custom `X-Operator-Token` header) is architecturally equivalent but
non-standard; it is NOT selected because the standard `Authorization: Bearer` header is
preferable for clarity and avoids inventing a bespoke convention without benefit.

Option C (full authentication framework) is NOT selected. Repository evidence does not
require it; the requirement is a minimal local gate, and a framework would add
unnecessary dependency and complexity to an offline, dependency-minimal system.

## Authorization Model

Single-credential gate: a valid presented credential grants operator read access to all
operator endpoints. There is no per-resource or per-role authorization (that is full RBAC,
out of scope). Authenticated operator access remains strictly read-only (enforced by the
existing router that registers only GET methods).

## SSE Security

- SSE_AUTH_REQUIRED = YES. `GET /api/v1/operator/events/stream` MUST pass the same auth
  guard as the REST endpoints; the stream MUST NOT bypass the auth boundary.
- SSE_INVALID_AUTH = 401 (missing/invalid credential rejected before any stream byte is
  sent, so the client never receives a stream without valid auth).
- SSE_VALID_AUTH = normal `text/event-stream` stream begins.
- RECONNECT_AUTH = every reconnect (new HTTP request carrying `Last-Event-ID`) MUST be
  re-authenticated independently; the credential is presented on each connection.
- Last-Event-ID interaction = unchanged. Authentication does not alter SSE event
  semantics, event ordering, durable seq, framing, or the snapshot->tail race behavior.
  `Last-Event-ID` remains a client resume cursor and is not durable.

## UI Security

- The offline UI (index + static assets) MUST NOT be served without valid authentication
  (the `/` and `/static/*` routes are gated).
- BROWSER_TOKEN_SOURCE = a local credential entry field in the operator UI (not a durable
  stored secret). On entry, the UI stores the credential for the page session and attaches
  it as `Authorization: Bearer <token>` on every operator fetch and on the SSE
  `EventSource`.
- REQUEST_HEADER = `Authorization: Bearer <token>` on all operator requests from the UI.
- SSE_AUTHENTICATION = the same `Authorization: Bearer <token>` header is sent on the
  `EventSource` connection (EventSource supports custom headers in modern browsers; if the
  runtime cannot set headers on EventSource, the UI falls back to authenticated REST
  polling rather than an unauthenticated stream).
- TOKEN_PERSISTENCE_POLICY = token held in memory for the page session only. Do NOT store
  the token in `localStorage` / `sessionStorage` unless explicitly justified; the default
  is non-persistent memory-only.
- LOGOUT/RESET_POLICY = clearing the credential entry / reloading the page drops the
  in-memory token; there is no server session to invalidate (stateless bearer check).

## Offline Requirements

WO-037-05 MUST preserve:

- OFFLINE_RUNTIME = YES
- NO INTERNET REQUIRED
- NO CLOUD IDENTITY
- NO CDN
- NO TELEMETRY
- NO EXTERNAL AUTH SERVICE

Token configuration:

- TOKEN_SOURCE = environment variable on the operator process (e.g. `OPERATOR_TOKEN`).
- TOKEN_FORMAT = opaque non-empty string (recommend high-entropy value; exact charset
  flexible).
- TOKEN_STORAGE = environment / process configuration only. MUST NOT be hard-coded in
  source, MUST NOT be committed to the repository, MUST NOT be written into a durable
  database.
- DEFAULT_BEHAVIOR = if no token is configured, the operator auth gate is DISABLED
  (unauthenticated access, matching current behavior) so existing local dev / test flows
  are not broken. This default MUST be explicit and documented; production deployment sets
  a token.
- MISSING_TOKEN_BEHAVIOR = if the token is not configured and the gate is disabled,
  requests proceed unauthenticated (dev/test). If the gate is enabled and a request
  presents no credential, respond 401.
- INVALID_TOKEN_BEHAVIOR = respond 401, never echo the presented token, never log it.

Do not write any actual secret value into this document or any repository file.

## Bind Address Policy

Decision required by architect. Two options:

- **Option A (keep 0.0.0.0:8010)**: bind stays as today; protection is provided solely by
  authentication. Least behavioral change.
- **Option B (change default to 127.0.0.1:8010)**: localhost-by-default, with LAN exposure
  requiring explicit `OPERATOR_HOST` override. Defense-in-depth, reduces attack surface
  even if a token is misconfigured. Changes the documented default behavior.

Recommendation (assessment, not decision): **Option B** as defense-in-depth, with
`OPERATOR_HOST` remaining an explicit opt-in for LAN exposure, PLUS Option A's
authentication. This is the recommended combination but the final bind policy is an
architecture decision and is NOT decided by this document. If changed, the migration/
compatibility implication is: existing deployments that rely on the current default bind
must set `OPERATOR_HOST=0.0.0.0` explicitly. Do NOT change the bind default silently
during implementation.

## Security Response Contract

| Condition | HTTP status | Rationale |
| --- | --- | --- |
| Missing credentials (gate enabled) | 401 | Authentication required |
| Invalid credentials (gate enabled) | 401 | Authentication failed |
| Valid credentials | 200 (REST) / 200 text/event-stream (SSE) | Access granted |
| Authenticated but forbidden (not applicable in single-credential model) | 403 reserved | For future RBAC; not triggered by MVP |
| Internal auth configuration/programming error | 500 | Server configuration/programming error |

Prevention (MUST):
- No secret leakage in responses.
- No stack-trace leakage in responses (existing generic "internal operator error" model).
- No token echo in responses.
- No raw token in logs; log only whether auth succeeded/failed, not the credential.

Rationale for 401 vs 403: 401 = authentication required/invalid (no/insufficient
credential). 403 = authenticated but not permitted — not reachable in the single-credential
read-only model, so 403 is reserved but unused in MVP.

## Security Headers / CORS

- CORS = OUT OF SCOPE / NOT ADDED. The operator UI is same-origin (served by the operator
  process) and the UI never calls a cross-origin API. No CORS middleware is added.
- Content-Security-Policy = SHOULD (operator-local default-src 'self'; no external
  resources allowed by design).
- X-Content-Type-Options = SHOULD (nosniff).
- Referrer-Policy = SHOULD.
- X-Frame-Options / frame-ancestors = SHOULD (DENY / 'none') — operator UI should not be
  framable.
- Cache-Control = SHOULD (no-store for operator API/UI responses given read-only
  sensitive data).

These are classified SHOULD (security hardening with no functional downside) rather than
MUST, to keep scope minimal. Final inclusion is an implementation/architect decision
within WO-037-05; they do not expand the boundary.

## Acceptance Criteria

Each AC is machine-testable.

- AC-01: unauthenticated REST request is rejected (401) when gate is enabled.
- AC-02: authenticated REST request succeeds when gate is enabled.
- AC-03: invalid token is rejected (401), token never echoed/logged.
- AC-04: missing token is rejected (401) when gate enabled.
- AC-05: SSE endpoint requires authentication (unauthenticated stream rejected 401).
- AC-06: valid SSE authentication succeeds (stream starts).
- AC-07: UI requests authenticate correctly (UI sends Authorization header; token entry
  works).
- AC-08: invalid credentials never leak a secret / stack trace.
- AC-09: programming errors remain 500 (generic, no internals).
- AC-10: durable dependency failures remain 503 (ReadDependencyUnavailableError path
  unchanged).
- AC-11: operator remains read-only (mutation methods still rejected 405).
- AC-12: durable core remains independent of auth (no durable-ingestion dependency on
  operator auth; no operator auth import in durable-core path).
- AC-13: no second event store.
- AC-14: no new durable authentication state.
- AC-15: offline operation preserved (no network/cloud/CDN dependency).
- AC-16: no external runtime dependency (stdlib-only auth).
- AC-17: existing WO-037-01..04 behavior remains green (regression).
- AC-18: SSE event semantics unchanged (ordering, durable seq, Last-Event-ID, framing,
  snapshot->tail race) — security non-regression.

Each AC uses the form GIVEN <state> WHEN <action> THEN <observable>, defined in the test
strategy.

## Security Non-Regression

WO-037-05 MUST NOT change: event ordering, durable seq, Last-Event-ID semantics, SSE
framing, snapshot->tail race behavior, read-only semantics, operator independence, or

## Test Strategy

- Unit tests: auth guard logic (constant-time compare, token-config resolution,
  enabled/disabled default).
- API tests: REST endpoints authenticated/unauthenticated (AC-01..04, AC-08..11).
- SSE tests: SSE requires auth; valid auth streams; invalid auth rejected before stream;
  reconnect re-auth (AC-05, AC-06, AC-18).
- UI tests: token entry + Authorization header on fetch and EventSource; no localStorage
  persistence (AC-07).
- Negative security tests: invalid token, missing token, no leak, no token in logs
  (AC-08).
- Regression tests: WO-037-01..04, durable/projection/checkpoint/replay (AC-17).
- No test may require network access (offline must be preserved).

## Threat Model

- ATTACKER = unauthenticated network client able to reach the operator bound address
  (e.g. on the LAN).
- ASSETS = durable canonical event feed, projected entities, projected relations,
  operator UI, health metrics.
- ENTRY_POINTS = `/api/v1/operator/*` REST, `/api/v1/operator/events/stream` SSE, `/`
  index, `/static/*`.
- TRUST_BOUNDARY = operator process boundary; client is untrusted until it presents the
  valid credential.
- THREATS:
  - Unauthorized LAN read of events/entities/relations (mitigated: auth gate).
  - SSE connection abuse (unauthenticated long-lived streams) (mitigated: SSE auth;
    connection limits deferred).
  - Credential leakage (mitigated: env-only storage, no commit, no log, no echo).
  - Error leakage / stack-trace disclosure (mitigated: generic 500/503, existing model).
  - Token logging (mitigated: log only auth success/failure, never the credential).
  - UI credential exposure (mitigated: memory-only page session, no localStorage).
- MITIGATIONS = see above.
- RESIDUAL_RISKS = transport is not encrypted at the operator process (HTTP); a
  credential captured on the wire is not protected by WO-037-05 (TLS is out of scope). On
  a hostile network, place operator behind an authenticated/reverse-proxy boundary or bind
  localhost.

## Risks

- R1 — Misconfigured/committed token (credential in VCS). Mitigation: env-only, no
  committed secret, token entry UI never persists.
- R2 — Token captured on unencrypted transport. Mitigation: bind-localhost by default
  (Option B) or run behind a TLS boundary; TLS out of scope.
- R3 — Auth disabled by default (no token configured) leaves operator open. Mitigation:
  explicit production token requirement; documented default.
- R4 — Regression of WO-037-01..04 / durable invariants. Mitigation: AC-11..AC-18
  regression tests; operator-only file boundary.
- R5 — UI EventSource header support variance. Mitigation: fallback to authenticated REST
  polling if EventSource cannot set headers.
