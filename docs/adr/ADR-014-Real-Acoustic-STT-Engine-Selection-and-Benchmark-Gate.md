# ADR-014 — Real Acoustic STT Engine Selection and Benchmark Gate

**Date:** 2026-09-02
**Status:** Proposed
**Deciders:** Chief Systems Architect

---

## Context

WO-039 established the STT seam, configuration, and bounded worker. The pipeline is:

```text
RTP → VAD → WAV master → STT seam → bounded STT worker
```

The WO-039-C work introduced the following artifacts:

- `ITranscriber` — the public transcription contract in `backend/app/contracts/audio.py`, deliberately not expanded by WO-039-C1.
- `AbstractSttAdapter` — the engine-neutral base class in `backend/app/audio/stt_seam.py` that a real engine adapter subclasses and that carries the offline `initialize(config)` lifecycle hook behind the adapter boundary.
- `SttConfig` — the frozen, validated offline STT configuration in `backend/app/audio/stt_config.py`.
- Bounded `SttWorker` — the queue-backed worker in `backend/app/audio/stt_worker.py` that runs transcription on a dedicated background thread and never blocks the RTP receiver, VAD, or recorder.
- Deterministic test transcriber — `DeterministicTestTranscriber` in `backend/app/audio/transcriber.py`, a deliberately non-acoustic test transcriber that maps a controlled `content_id` to a known transcript via a configurable phrase table. It is NOT production speech recognition.

Current state (verified):

- No production acoustic adapter is registered. `build_transcriber` in `backend/app/audio/stt_seam.py` resolves a registered engine factory via `register_engine`; for a *recognised* engine with no registered adapter it raises `SttEngineUnavailableError`, so there is never a silent fallback to `DeterministicTestTranscriber` in a production STT configuration.
- `register_engine` is called only in tests, with a non-acoustic fake adapter (see `backend/tests/test_wo039c_stt.py`).
- The following are recognized candidates only:

```text
faster_whisper
vosk
```

  `SUPPORTED_ENGINES = frozenset({"faster_whisper", "vosk"})` in `backend/app/audio/stt_config.py` is the *recognised* set, explicitly not a production choice.

- Both the configuration and the worker architecture explicitly preserve the state that engine selection is deliberately `NOT_YET_JUSTIFIED` (WO-039-C). `stt_config.py` states this in its `SUPPORTED_ENGINES` comment; `stt_worker.py` states that it "never... does engine selection (the engine stays `NOT_YET_JUSTIFIED`; C3 consumes the abstract adapter)."
- The repository does not contain an approved STT benchmark protocol or an accepted engine-selection decision. No ADR currently authorizes production engine selection.

## Problem

Implementing a real acoustic engine before objective evaluation would create an unjustified technology lock-in and would violate the engine-neutral C1/C2/C3 architecture. The seam, configuration, and worker were deliberately built to be engine-neutral; binding the production runtime to a specific engine without a reproducible, evidence-backed comparison would discard that neutrality and commit the system to a technology choice made in the absence of measured evidence.

## Decision

> Production acoustic STT engine selection is gated by a reproducible benchmark on representative real radio audio followed by an explicit architecture decision.

The current decision remains:

```text
NOT_YET_JUSTIFIED
```

This ADR itself does NOT select an engine. It establishes the gate; the gate, once satisfied, is the basis for a separate engine-selection decision.

## Candidates

The recognized candidate set is:

```text
faster_whisper
vosk
```

```text
Candidate ≠ Authorized Production Engine
```

Recognition as a candidate carries no authorization to implement, register, or integrate the engine.

## Required Benchmark

The minimum mandatory benchmark:

Dataset:

- real radio transmissions generated by the actual project audio pipeline;
- representative G.711 A-law / project-native WAV masters where applicable;
- representative radio speakers and sources;
- realistic acoustic/noise conditions actually encountered;
- representative callsigns and tactical vocabulary;
- manually verified ground-truth transcripts.

Minimum: `50 independently verified radio transmissions`.

If fewer than 50 usable real recordings exist at execution time, the benchmark report must explicitly document the limitation and cannot silently redefine the requirement. Synthetic speech alone is NOT acceptable.

## Required Metrics

The benchmark must measure:

### Recognition

- WER
- CER
- callsign accuracy

### Performance

- end-to-end latency
- real-time factor

### Resource usage

- CPU
- RAM
- GPU utilization where applicable
- VRAM where applicable

### Reliability

- failure rate
- timeout rate

Each metric must be defined sufficiently clearly for reproducible comparison. For example:

```text
RTF = processing time / audio duration
```

Callsign accuracy is scored as the fraction of ground-truth callsigns correctly transcribed, over the total number of ground-truth callsigns present across the benchmark dataset; a callsign is counted correct only if it appears verbatim in the transcript.

## Benchmark Method

Require identical, for every candidate:

- dataset;
- language;
- normalized audio format;
- hardware.

Record separately:

- cold-start measurements;
- warm/inference measurements.

Record engine configuration and model variant. Failures must be counted explicitly. WER/CER calculations must use the manually verified reference transcripts. A failed transcription must not be allowed to disappear from the benchmark denominator. No network-dependent model download may be required by the benchmark execution.

## Approval Gate

### Mandatory gate

A candidate must demonstrate acceptable:

- recognition quality;
- callsign accuracy;
- operational latency / RTF;
- reliability;

before being considered for production.

### Observational measurements

CPU / RAM / GPU / VRAM are recorded and used for operational suitability comparison. They are observational inputs to the decision, not standalone pass/fail criteria.

### Proposed thresholds

Where the repository has no existing ratified numeric threshold, thresholds are marked:

```text
PROPOSED — NOT YET RATIFIED
```

No arbitrary threshold is presented as an existing project requirement. The existing unratified Sprint 08 target:

```text
recognition accuracy >85%
```

may be mentioned only as an existing backlog aspiration, NOT as an accepted approval criterion.

## Decision Rule

The benchmark result must lead to one of:

1. Candidate A selected.
2. Candidate B selected.
3. Neither candidate passes the mandatory gate.

If neither passes:

```text
NO PRODUCTION STT ENGINE AUTHORIZED
```

The decision process does not force a winner.

## Required Evidence Artifact

Define a mandatory benchmark report, following repository naming convention. Suggested logical artifact:

```text
STT Engine Benchmark Report
```

The report must contain:

- dataset;
- ground truth method;
- hardware;
- candidate versions / configuration;
- all metrics;
- failures;
- comparative analysis;
- recommendation;
- final decision.

The exact report filename can be assigned later by the benchmark Work Order if repository convention requires it.

## Authorization Rule

This ADR explicitly prohibits, until ALL of the following are true:

1. benchmark executed;
2. benchmark report recorded;
3. mandatory gate passed;
4. production engine decision accepted by the Chief Systems Architect;

the following activities:

- production STT adapter implementation;
- production engine registration;
- engine-specific runtime integration.

## WO-008-004

`WO-008-004 — Speech Recognition Pipeline` is addressed explicitly. It remains a PLANNED backlog item (`docs/work_orders/SPRINT_08_BACKLOG.md`). Its Faster-Whisper wording is not sufficient to override the current `NOT_YET_JUSTIFIED` architecture gate. This ADR does NOT modify `SPRINT_08_BACKLOG.md` and does NOT delete or rename WO-008-004.

## Consequences

Positive:

- no premature engine lock-in;
- reproducible evidence;
- preserves the engine-neutral seam;
- supports auditable production selection.

Negative:

- production acoustic STT implementation is delayed until benchmark evidence exists;
- representative recordings and manual ground truth are required.

## Non-Goals

This ADR explicitly does NOT authorize:

- real STT adapter implementation;
- model installation;
- model download;
- runtime integration;
- callsign AI implementation;
- schema / database changes;
- replay / re-STT implementation;
- changes to the C1/C2/C3 interfaces;
- changes to the RTP / VAD / recording pipeline.
