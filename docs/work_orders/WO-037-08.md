## 2. Architectural Authority

- **ADR-013 (Accepted)** — Severity Ruleset Single-Source Architecture. Distinguishes the MACHINE-READABLE RULESET (authoritative rule content) from the BASELINE CLASSIFIER (sole semantic owner of classification). The implementation preserves this distinction.
- **ADR-012 (Accepted)** — Severity taxonomy and classification semantics. `INFO < WARNING < THREAT < CRITICAL`, precedence and the NO SILENT RESOLUTION invariant are unchanged.

## 3. Purpose

Convert the remaining ADR-013 governance requirements into enforceable release controls:

1. CI enforcement of severity ruleset validation.
2. Release immutability enforcement for released severity rulesets.

## 4. Scope Implemented

The implementation delivers the enforceability layer only. It does not redesign the severity architecture and does not change severity semantics.

## 6. CI Platform

**GitHub Actions** — `.github/workflows/severity-governance.yml`. This is the repository's first CI workflow. It runs on `push` and `pull_request`, uses Python 3.11, and is a HARD GATE: every step must pass, no `continue-on-error`, no warning-only checks. It never regenerates/commits files and never invokes an external rules service.

## 7. Release Ledger Mechanism

`docs/governance/SEVERITY_RELEASE_LEDGER.toml` is the **authoritative release history**. It is NOT a regenerated checksum file. Each release record binds:

```text
released semantic version
+ historically released artifact bytes (FROZEN SHA-256)
+ historical release commit
= immutable release identity
```

The initial release record anchors `SEVERITY-RULES-v1.0.0` to the historical commit
`7ccea777b34ff1f9af363021efe313e21ef87184` (WO-037-07, which introduced the
authoritative machine-readable artifact). The validator independently proves
that the artifact bytes at that commit hash to the frozen
`84e702757d387051ae73c61becde6bdb193d9035c4ff6eb3fc101006e5e3b204`.

## 8. Release Immutability Semantics

Enforced by `scripts/validate_severity_release.py` (read-only, offline,
deterministic, stdlib-only, fail-closed):

| Case | State | Result |
| --- | --- | --- |
| A | same version + same bytes (current SHA == released SHA == historical SHA) | PASS |
| B | same version + different bytes | FAIL (same-version content mutation) |
| C | new semantic version + new artifact + new release identity | POTENTIALLY PASS (subject to normal validation) |

The validator rejects: duplicate versions, duplicate release identities,
malformed/incomplete records, empty values, invalid SHA-256, missing historical
commit, missing historical artifact, historical hash mismatch, artifact-path
mismatch, missing release record, and same-version mutation.

## 9. Static Single-Source Detector

`scripts/check_severity_single_source.py` uses deterministic AST analysis of
`backend/app/operator/severity.py` (never edits it) to detect forbidden
independent hardcoded semantic rule content:

- independent semantic rule table (literal `rule_id` / `event_type` / `source` / `severity`);
- hardcoded `BaselineRule(...)` constructions carrying literal semantic values;
- semantic fallback mappings;
- authoritative-source bypass (module does not invoke `load_ruleset()` nor reference `RULESET_PATH`).

It does NOT falsely reject legitimate taxonomy (`Severity` enum,
`_VALID_SEVERITIES`, `_VALID_RULE_STATUSES`, schema field sets, version regexes,
loader, precedence, classification functions).
